Visão Executiva
& Princípio Central

Por que adotar IA de forma estruturada — não pontual

O Problema

O que acontece sem arquitetura

❌ Sem arquitetura corporativa

  • Cada agente acessa fontes diferentes
  • Regras de negócio aplicadas de forma inconsistente
  • Respostas com níveis distintos de qualidade
  • Sem rastreabilidade ou auditoria
  • Segurança e conformidade como reflexo tardio
  • Duplicação de integrações e retrabalho
  • Shadow AI prolifera sem controle

✅ Com arquitetura corporativa

  • Fonte única de verdade para todos os agentes
  • Menos retrabalho e duplicação de integrações
  • Rastreabilidade completa de ações
  • Segurança e conformidade desde o dia 1
  • Escala sem perder controle
  • Usuário continua nas interfaces conhecidas
  • Qualidade medida continuamente
"IA escala valor apenas quando decisões automatizadas são confiáveis, governadas e mensuráveis"
Conceito-chave

O que é Arquitetura Corporativa de IA?

Desenho integrado de processos, dados, identidade, segurança, governança e experiências de usuário para que agentes operem de forma previsível, escalável e alinhada às políticas da organização.

Microsoft 365 Copilot

Experiência do usuário e grounding com dados do Microsoft Graph

Foundry + Copilot Studio

Agentes, orquestração, avaliações e lógica de negócio

Microsoft Fabric

OneLake, lakehouses, warehouses e modelos semânticos

Purview + Entra ID

Classificação, proteção, identidade e controle de acesso

Exemplos Práticos

IA na prática corporativa

1

Atendimento Executivo

Diretor pergunta no M365 Copilot por que a margem caiu. O Copilot encaminha para um agente de domínio, que consulta dados financeiros governados no Fabric via modelo semântico e devolve uma resposta coerente com as permissões do usuário.

2

Agente de Operações

Agente no Copilot Studio recebe pedido para investigar aumento de incidentes. Consulta métricas no Fabric, aplica regras de negócio do domínio e usa guard rails para bloquear ações fora do escopo. Resultado: análise auditável alinhada às políticas.

3

Governança em Escala

RH, Finanças e Operações publicam agentes distintos. Mesmo com finalidades diferentes, todos seguem o mesmo padrão de identidade, acesso, classificação, observabilidade e avaliação. Diversidade de agentes, base comum de controle.

Guard Rails

Controle de Segurança Transversal

Guard Rails são controles que permeiam todas as operações de agentes — não são um módulo separado, são uma camada de proteção presente em cada interação.

Prompt Shields

Detecta e bloqueia prompt injection — ataques que tentam manipular o comportamento do agente via instruções maliciosas

Content Safety

Filtra categorias de risco: violência, NSFW, discurso de ódio. Validação automática de entradas e saídas

Purview Labels

Controla qual agente acessa qual dado baseado em classificação de sensibilidade — Public, Internal, Confidential, Highly Confidential

PII Detection

Remove informações pessoais identificáveis antes de retornar respostas, prevenindo vazamentos inadvertidos

Audit Logs

Toda ação de agente é registrada para conformidade. Logs enviados ao Purview para auditoria completa e trilha de evidências

Evaluators

Medição Contínua de Qualidade

Evaluators validam se os agentes estão operando corretamente — não apenas se respondem, mas se respondem com qualidade e segurança.

DimensãoO que medeExemplo de métricaAção se falhar
GroundednessResposta baseada em dados reais?>95% = OKReject + log
Task AdherenceAgente fez o que foi pedido?>90% = OKFeedback loop
ToxicityConteúdo prejudicial presente?0 = OKBloqueia resposta
SegurançaDados sensíveis expostos?0 = OKBloqueia + alerta
DriftPerformance degradou?Δ <5% = OKAlerta + retraining

Avaliador valida resposta sobre margem: groundedness = 95%, task adherence = 98%, sem vazamento de dados → aprovada e entregue ao usuário.

Microsoft Fabric

OneLake — O Lago Unificado

Um único lago de dados lógico por tenant, construído sobre ADLS Gen2. É o equivalente corporativo do OneDrive para dados — provisionado automaticamente quando você ativa o Fabric.

OneLake

Camada única de armazenamento corporativo no tenant.

→

→

→

Consumers

Interoperabilidade

Estrutura

Shortcut = referência virtual a dados externos (ADLS Gen2, S3, GCS, Dataverse). Agentes consultam como tabela local. Zero cópia, dados sempre frescos, segurança herdada automaticamente.

Formato de Dados

Delta Lake — Por que importa?

Fabric padroniza em Delta Lake: formato open-source que adiciona transações ACID, validação de schema e histórico sobre Parquet. Todo engine (Spark, SQL, Power BI) que escreve dados cria Delta tables.

PropriedadeParquet PuroDelta Lake (Fabric)
ACID Transactions❌ Não✅ Sim
Schema Enforcement❌ Não✅ Sim — evita dados "sujos"
Time Travel❌ Não✅ Sim — consulta versões passadas
Data Rollback❌ Não✅ Sim — reverte escritas ruins
PerformanceBásico⚡ V-Order optimization
Auditoria❌ Não✅ Sim — Delta history completo

Por que isso importa para agentes?

Agentes confiam que dados são corretos (ACID). Múltiplos agentes leem simultaneamente a mesma versão consistente. Schema enforce previne dados corrompidos. Histórico completo = auditoria garantida.

Interface SQL

SQL Analytics Endpoint — Como Agentes Acessam Dados

Cada Lakehouse em Fabric provisiona automaticamente um SQL Analytics Endpoint — endpoint TDS que expõe Delta tables como tabelas SQL padrão.

Capacidades

  • SELECT contra Delta tables (incluindo Shortcuts)
  • Views, funções, stored procedures T-SQL
  • Row-Level Security (RLS) automático
  • Conexão com Power BI (Direct Lake)
  • Azure Data Studio, SSMS, qualquer cliente TDS

Performance

  • Sincronização Lakehouse → SQL: <1 minuto
  • V-Order: Spark grava Parquet otimizado para leitura SQL
  • Estatísticas e índices automáticos (sem ação manual)
  • Powered pelo mesmo engine do Fabric Data Warehouse
-- Agente consulta dados Gold via SQL Analytics Endpoint SELECT p.ProductName, SUM(s.Amount) AS TotalSales FROM Gold.Products p INNER JOIN Gold.Sales s ON p.ProductID = s.ProductID WHERE s.Date >= DATEADD(month, -3, GETDATE()) GROUP BY p.ProductName ORDER BY TotalSales DESC -- RLS já filtrou dados conforme identidade Entra ID do agente

Governança

Entra ID Agent Identity — Agentes têm identidade

Cada agente recebe uma identidade corporativa distinta no Microsoft Entra ID — não apenas um service principal genérico, mas uma identidade com contexto, rastreabilidade e políticas adaptativas.

AspectoService Principal (Legado)Entra Agent ID (Novo)

Classificação de Dados

Purview Sensitivity Labels — 4 Níveis de Proteção

Hierarquia de classificação com proteção progressiva. Labels aplicados automaticamente aos dados no OneLake, herdados por todos os consumidores.

LabelCenário de usoProteçãoAcesso por Agente
🟢 PublicCatálogo de produtos, preços públicosNenhuma criptografia✅ Automático
🔵 InternalDocumentos operacionais, comunicadosMarca d'água✅ Automático
🟡 ConfidentialContratos, planos de vendas, financeiroCriptografia + restrição⚠️ Requer Conditional Access
🔴 Highly ConfidentialPII (CPF, email, fone), segredosCriptografia forte + rígida❌ Bloqueado (human-in-loop)

Exemplo de bloqueio automático

Agente tenta acessar dados rotulados como "Highly Confidential" → Guard Rail intercepta → registra tentativa → bloqueia acesso → log enviado ao Purview para auditoria. Tudo automático, sem intervenção humana manual.

Row-Level Security

RLS — Agente vê apenas o que deve ver

O SQL Analytics Endpoint aplica Row-Level Security automaticamente baseado na identidade Entra ID do agente. Um agente de vendas da LATAM nunca vê dados da EMEA.

Como funciona

1

Agente solicita token JWT ao Entra ID com seu ClientID

2

JWT carrega roles e contexto do agente

3

SQL Endpoint valida token + consulta Purview label da tabela

4

RLS aplica filtro automático — agente recebe dados filtrados

5

Audit log registrado: quem acessou, o quê, quando, resultado

Exemplo prático

Agente eng-sales-001 com role LATAM,EMEA executa:
SELECT * FROM fct_Orders


→ Tabela tem 5.000 linhas no total
→ RLS filtra automaticamente
→ Agente recebe 1.245 linhas (só LATAM+EMEA)
→ Sem consciência de que existem mais dados

Segurança Multinível

4 Camadas de Validação em Cada Acesso

1. Entra ID

Autentica o agente e valida o token JWT.

→

2. Conditional Access

Avalia risco, horário, IP e contexto do acesso.

→

3. Purview Labels

Define a sensibilidade e o nível de proteção do dado.

→

4. RLS + PIM

Filtra, aprova ou bloqueia o acesso antes da consulta.

1

Entra ID — Autenticação

Valida JWT token, verifica assinatura e expiração. Token inválido = acesso negado imediatamente.

2

Conditional Access — Segurança Adaptativa

Avalia contexto: IP, horário, risco, dispositivo, localização. Acesso fora do horário comercial pode exigir aprovação adicional.

3

Purview Labels — Classificação dos Dados

Consulta o label da tabela solicitada. Define o nível de proteção aplicado: nenhum, RLS, ou bloqueio + PIM.

4

RLS + PIM — Filtragem e Aprovação

Public/Internal: RLS direto. Confidential: RLS + Conditional Access. Highly Confidential: PIM (aprovação humana obrigatória em tempo real).

Todo acesso, aprovado ou negado, gera audit log estruturado com JSON completo: quem, o quê, quando, de onde, resultado, número de linhas, nível de risco.

Phase 3 — Pré-requisitos

As 3 Competências Críticas para Escala

Para escalar com sucesso, 3 competências devem estar em Level 300 — não é apenas tecnologia, é mudança organizacional.

1️⃣ Business Process — L300

Processos documentados, medidos e prontos para automação. Dicionário de dados consistente. Sem "João sabe fazer isso".


Exemplo: "Triagem de suporte" documentado em Visio, SLA de 4h, pronto para agente.

2️⃣ Staff & Training — L300

Treinamento obrigatório (não voluntário). Managers adotam primeiro. Champions program estruturado (4h/mês).


HR torna mandatory. Manager faz 40h de "AI for Managers". Equipe treinada pelo manager.

3️⃣ Content Governance — L300

Documentação clara e atualizada. Sensitivity labels aplicados. Permissões corretas. Ownership definido.


Nenhum "shared with everyone". Todos os docs têm owner, version e sensitivity label.

Pesquisa Microsoft: adoção trava em 20-30% quando essas 3 competências não chegam ao Level 300. Não é problema técnico — é problema organizacional.

Cenários A vs B

Self-service vs dados tratados — e como o modelo híbrido maduro une o melhor dos dois mundos

Estratégias de Adoção

Cenário A vs Cenário B

🅰️ Cenário A — Self-Service

Agentes autônomos com acesso direto a dados variados

✅ Prós

  • Alta inovação, experimentação rápida
  • Flexibilidade total para novos casos
  • Menor dependência de TI

❌ Contras

  • Risco de Shadow AI
  • Inconsistência entre respostas
  • Custo variável e difícil de controlar
  • Sem auditoria centralizada
  • Vazamento de PII

🅱️ Cenário B — Dados Tratados

Agentes controlados acessando Fabric Gold via SQL Endpoint

✅ Prós

  • Governança e conformidade garantidas
  • Consistência de respostas entre agentes
  • Auditabilidade completa
  • Controle de custos via quotas

⚠️ Desafios

  • Menor agilidade inicial
  • Dependência de pipeline de dados
  • Requer planejamento antecipado
Conclusão Estratégica

O Modelo Ideal: Híbrido e Evolutivo

Não é uma escolha binária. O modelo maduro combina os dois cenários com guardrails que evoluem com a maturidade.

Curto Prazo

Cenário B primeiro: dados tratados e controles fortes.

→

Médio Prazo

Cenário A controlado: autonomia dentro de sandbox.

→

Longo Prazo

Modelo híbrido maduro com liberdade e governança.

1

Curto prazo (0-4 meses) — Cenário B primeiro

Começar com M365 Copilot + dados tratados. Estabelecer guardrails, classificação de dados, audit logging. Segurança como fundação, não como reflexo tardio.

2

Médio prazo (4-10 meses) — Cenário A controlado

Self-service dentro de um sandbox governado. Copilot Studio com conectores controlados. Inovação dentro dos limites estabelecidos.

3

Longo prazo (10+ meses) — Híbrido Maduro

Alguns agentes mais livres em sandbox com guardrails automáticos. Maioria governal com Foundry + Fabric. Inovação rápida dentro de limites claros e mensuráveis.

"Segurança e consistência primeiro, inovação rápida dentro de guardrails estabelecidos"

Ação Imediata

Próximos Passos — As 5 Primeiras Ações

1

Esta semana — Identificar Sponsor Executivo

Sem patrocínio de C-level, a iniciativa não escala. Identificar o sponsor certo é a ação mais crítica e imediata.

2

Semanas 1-2 — Montar a Equipe Multidisciplinar

Definir RACI: Data Engineer, AI Engineer, Business Owner, Compliance, HR. Cada papel tem responsabilidade clara.

3

Semanas 2-4 — Mapear e Classificar Dados

Auditar dados dos 3-5 use cases candidatos. Aplicar Purview sensitivity labels. Meta: 80% classificado antes do PoC.

4

Mês 1 — Selecionar o Primeiro Use Case

Critérios: alto valor de negócio, baixo risco técnico, processo já documentado, não voltado ao cliente externo.

5

Meses 1-2 — Lançar PoC com 10 Usuários

M365 Copilot + dados classificados. Medir desde o dia 1. Documentar aprendizados. Construir o business case para Phase 3.
